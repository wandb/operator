# Secrets in server manifests

Top-level `secrets` declares the Secrets that a server version needs. The operator
creates them before migration Jobs and application reconciliation. The contents
can be generated by the operator or populated by a workload with a scoped Role.

```yaml
secrets:
  - name: session-key
    generated:
      length: 32
      type: password
  - name: weave-worker-auth
    useExactName: true
    generated:
      length: 32
      type: password
  - name: wandb-internal-signer
    useExactName: true
```

Names default to `<cr-name>-<name>`. `useExactName: true` uses the declaration's
name verbatim. All Secrets are Opaque and live in the CR's namespace. Newly
created Secrets receive a CR owner reference and operator labels. Existing ownerless
Secrets are adopted by the current CR; their data and other metadata are
preserved. Secrets owned by another resource are rejected.

When `generated` is absent, the operator creates an empty Secret only if missing.
It never fills, clears, or resets its contents. This lets the internal signer
initialize its declared Secret with only name-restricted `get/update` permission;
it does not need namespace-wide Secret creation permission.

When `generated` is present, the operator generates a random value in the `key`
entry if that key is missing. Other data entries and existing generated values
are preserved. An empty `generated: {}` requests the existing default generator
with a length of 32. `length` and `type` retain their legacy generation behavior;
`type: password` is the form used by current manifests. This change does not add
new generators or key rotation.

Only generated declarations register a selector in `status.generatedSecrets`.
Existing environment sources using `type: generatedSecret` and the declaration's
logical name continue to work with the unified schema. Empty declarations do not
advertise a nonexistent generated `key` entry.

Legacy top-level `generatedSecrets` remains supported for previously published
server versions. Its entries are normalized to declarations with `generated`
set, preserving exact/prefixed names, value lengths, and status selectors. A
manifest can use both forms for distinct Secrets, but duplicate logical names
or resulting Kubernetes names are rejected before writes. New `secrets` lists
are combined across manifest files; the legacy merge behavior is unchanged.

The local `0.86.0` manifest uses the unified declaration for its two
operator-generated values and its signer-populated Secret. Published manifests
must require an operator version supporting `secrets` before migrating to it.

Removing a declaration does not immediately delete its Secret. Reconciled Secrets
are tracked with a manifest-Secret label, so cleanup also covers declarations
removed from a later manifest. Legacy generated Secrets are additionally found
through `status.generatedSecrets`. Cleanup does not need to fetch the manifest.

On CR deletion, the global `spec.retentionPolicy.onDelete` controls retention:

- `detach` (the default) removes only the deleting CR's owner reference and keeps
  Secret contents and any unrelated owner references intact.
- `purge` keeps the owner reference so normal garbage collection can delete the
  Secret with its owning CR.

The cleanup finalizer is retained if detaching a Secret fails. A replacement CR
that declares the same Secret adopts it when it has no owner, using the new CR's
UID without regenerating existing values. Secrets with other owners are not
claimed. Declaring a Secret does not itself grant workload read/write access;
ServiceAccounts and Roles control access separately.

These declarations describe version-specific server Secrets. Managed infrastructure
and other operator features continue to reconcile their own credentials.
